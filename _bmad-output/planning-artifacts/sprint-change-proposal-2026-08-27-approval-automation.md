## 1. Issue Summary

### What triggered it

On 2026-08-27 Oleg asked what has to happen for a commit on `main` to reach production. The answer
is a five-step chain, and three of its steps are human acts with no machinery behind them at all:

| # | Step | Today |
|---|---|---|
| 1 | Merge to `main` | automatic |
| 2 | Dispatch `deploy-preprod.yml` | human, one click |
| 3 | Run `RVC-v1.1` against the stand | **human, ~12 checklist items** |
| 4 | Dispatch `record-preprod-candidate.yml` with `validated: pass` | **human, a second dispatch** |
| 5 | Append a row to `docs/prod-releases.md`, then dispatch `deploy-prod.yml` | **human, a commit** |

Oleg's instruction, verbatim: *"3. считаем если задеплоили на preprod, то прошли. 4. это должно быть
автоматически. 5. автоматически после 3 шага"*. Confirmed through two explicit choices: step 4 →
**"Автомат + переписать смысл"**; step 5 → **"Автоматом + переписать регламент"**.

### The two decisions, stated precisely

- **(a)** Recording a PRE-PROD candidate becomes a **consequence of a successful PRE-PROD deploy**,
  not a separate dispatch carrying a human verdict. `preprod-<sha>` stops meaning *"this commit was
  validated"* and starts meaning *"this commit reached PRE-PROD"*.
- **(b)** The production approval stops being a row appended **before** the dispatch. **The dispatch
  of `deploy-prod.yml` is the approval**, and the ledger records it **after the fact**.

### Why this is not a small change

`preprod-<sha>` is load-bearing in three separate places, and (a) changes what all three are reading:

- **FR16 / `#d2`** — Story 6.5's promotion guard, shipped 2026-08-27, refuses any release whose
  commit has no `preprod-<sha>`. Its own job name is *"Promotion guard -- refuse a commit PRE-PROD
  never validated"* (`deploy-prod.yml:386`).
- **`#d38` §2** — the recorder was made dispatch-only **on purpose**, and the reason recorded there
  is verbatim the thing decision (a) now accepts: *"если запись автоматическая, `preprod-<sha>`
  означает «этот коммит был задеплоен» — а Story 6.5 читает этот же тег как «этот коммит был
  ВАЛИДИРОВАН» (FR16)."*
- **`docs/production-approval-regulation.md`** — its precondition section is written on top of that
  meaning.

And (b) removes the only step in the chain that a human currently *must* perform in a file, which
is the whole reason `docs/production-approval-regulation.md` exists (NFR9, `#d5`: Forgejo has no
approval gate, so the document is the control that exists instead).

### Evidence that the cost is smaller than it looks

**`docs/prod-releases.md` has zero rows.** No production release has ever been approved under this
regulation. Nothing recorded is being rewritten; a rule that has never been exercised is being
changed before its first use. This is the cheapest possible moment.

## 2. Impact Analysis

Nine findings. Six are measured on the live instance today, 2026-08-27, and each names how.

### M1 — a workflow **cannot** commit the ledger row. Measured.

`GET /api/v1/repos/CRM/fe-prionex/branch_protections/main`:

```
enable_push                        False
enable_push_whitelist              False
push_whitelist_usernames           []
enable_status_check                True
```

`enable_push: false` with an empty whitelist means **direct push to `main` is refused for every
account, admin included**. There is no bypass to grant.

🔴 **This retires the premise the decision was framed on.** The repository-write credential Story
5.4 declined to open would **not** have made an automatic ledger row possible. The alternative —
the workflow opens a PR — reintroduces a human merge, i.e. relocates the manual step rather than
removing it, and makes the ledger depend on eight required status checks passing.

### M2 — every cell the ledger needs is **already recorded and queryable**, independently of job logs. Measured.

Run id `1618` (= run **705**, `deploy-prod.yml`), read from `GET /actions/runs`:

```json
{ "id": 1618, "workflow_id": "deploy-prod.yml", "index_in_repo": 705,
  "trigger_user": { "login": "platform-admin", "email": "kuksaworld@gmail.com", "is_admin": true },
  "commit_sha": "ff236c89beca88151dfd2754a24c315b6f52a001",
  "prettyref": "story-6-7/impl", "status": "...", "started": "...", "stopped": "...",
  "event_payload": "{\"inputs\":{\"rollback\":\"true\",\"tag\":\"sha-a99ccd44c5a3-prod\"}, ...}" }
```

Mapped against `docs/prod-releases.md`'s ten columns:

| Column | Source | Derivable? |
|---|---|---|
| `Date (UTC)` | `started` | ✅ |
| `image_tag` | `event_payload.inputs.tag` | ✅ |
| `Candidate` | derived from the tag's 12 hex (`#d18` §3) | ✅ |
| `prod_tag` | `event_payload.inputs.tag` | ✅ |
| `Approved by` | `trigger_user.login` | ⚠️ **an account, not a name — see M3** |
| `Waiver?` | — | ❌ human only |
| `Approval start (UTC)` | `started` | ✅ (meaning changes — see M7) |
| `Approval end (UTC)` | `stopped` | ✅ (meaning changes — see M7) |
| `Deploy run id` | `index_in_repo` | ✅ |
| `Note` | — | ❌ human only |

**Eight of ten cells are already machine-recorded, over the REST API, with no dependency on job
logs.** That matters specifically here: the six `log_in_storage=f` observations across Stories 5.3
and 5.4 are the stated reason the ledger lives in a file at all. `action_run` rows are not logs and
are not subject to that.

This is also exactly the shape `retro-D4` already blessed: *run ledgers close by query, attributed
by `commit_sha`*.

### M3 — 🔴 attribution is an **account**, and there is only one. Measured, all 717 runs.

Walked to natural termination (15 pages, 717 runs, matching the reported `total_count`):

```
distinct trigger_user: {'platform-admin': 705, 'forgejo-actions': 12}
```

**There is no per-person attribution in this repository. There never has been.** Every run Oleg has
ever dispatched and every run the agent has ever dispatched is recorded as the same `is_admin: true`
account.

Against the regulation's own rule for that column — *"a name — never a role, never «whoever is
around»"*, itself inherited from `deferred-work.md:23` (*"**Owners are NAMES or STORY NUMBERS**"*) —
an automatically-generated `Approved by` cell **cannot be a valid approval record today**. It is not
that the value would be wrong; it is that it is **unfalsifiable**: it cannot distinguish Oleg from
the agent, which under the standing coordinator/dev-agent split dispatches through the same account.

This is the single largest cost in the change, and it is fixable — see §3, and the two options put
to Oleg there.

### M4 — the API reports `event: ""` for dispatches. Measured.

Of 717 runs: `push` 400, `pull_request` 134, `create` 2, and **`""` for 181** — including run 1618
above, which is unambiguously a `workflow_dispatch` (its `event_payload` carries `inputs`). The
count of runs reporting `event == "workflow_dispatch"` is **zero**.

A ledger generator filtering on `event` would produce an empty ledger. The trigger must be inferred
from `event_payload` containing an `inputs` key, plus `workflow_id == "deploy-prod.yml"`. Written
down here so it is not rediscovered at implementation time. (This is an API-projection quirk only —
inside a workflow `github.event_name` is correct, as `#d21` measured on run 631.)

### M5 — decision (a) **deletes guard G1** and its discriminating row.

`#d38` §6's live outcome matrix has six guards. G1 is *"вердикт = `pass`"*, with the refusal row
**run 1218** (`validated=fail` — refused on the first line, zero network calls).

With no verdict input, **G1 has nothing to check and ceases to exist.** Run 1218 becomes the record
of a guard that no longer ships.

The other five survive intact, and it is worth being precise about why: G2 (`-preprod` suffix), G3
(shape + exactly 12 hex), G4 (`keep_pattern` protection), G5 (the stand provably runs this digest),
G6 (artifact labels agree with the derivation) are all assertions about **the tag's shape and the
stand's actual state** — none of them reads a human claim. So `retro-E5` (*every guard ships with a
live outcome matrix including a discriminating run*) stays satisfied for five of six, and is
unmeetable for the sixth only because the sixth is gone.

⚠️ **One nuance that must not be oversold.** If the record becomes a job inside `deploy-preprod.yml`
immediately after the deploy, **G5 becomes trivially true** — the deploy just put that digest there.
It should be kept anyway (it is nearly free and it catches a concurrent overwrite), but it stops
being an independent check and must stop being *described* as one.

### M6 — `RVC-v1.1` loses its only mechanical consumer.

Today the checklist's derived verdict is an **input** to a workflow. After (a), **no workflow reads
it.** It survives only as a document the approver is instructed to read — which is precisely the
status the regulation already assigns to `docs/preprod-candidates.md` (*"The approver reads
`docs/preprod-candidates.md`, not only the registry tag"*).

The checklist is not being retired and this proposal does not propose retiring it. But it stops
being enforceable by machinery, and the regulation must say so instead of implying otherwise.

### M7 — the freeze window loses its start event.

`docs/production-approval-regulation.md`, `## The freeze window`: *"PROD's window will run **from the
approval row being appended** to that smoke check passing"*.

With no append, there is no start. The window must be redefined. The natural replacement costs
nothing and is already measured (M2): **the window runs from the `deploy-prod.yml` run's `started`
to the smoke check's outcome** — and the smoke check now exists (Story 6.7, `#d50`, run 705 green).

Consequence for `docs/prod-releases.md`: the columns `Approval start (UTC)` / `Approval end (UTC)`
no longer describe a human reading a file. They must be renamed, not merely re-sourced.

### M8 — ⚠️ the fact that cuts **against** decision (a), recorded because it is true.

`#d39` established that 8 of `RVC-v1.1`'s 12 items were unexecutable because of a foreign CORS
configuration, making the honest derived verdict `fail` for **any** candidate — which is why
`sha-a99ccd44c5a3-preprod` shipped `7/12 pass, 5 BLOCKED` under Oleg's written waiver
(`#d40`/`#d41`).

**That blocker is fixed.** Measured 2026-08-27 with `GET` (an earlier `curl -I` measurement was
wrong and is superseded): PRE-PROD Kong returns
`Access-Control-Allow-Origin: https://crm.preprod.crm-prionex.online` with
`Access-Control-Allow-Credentials: true`, and does **not** echo a foreign `Origin`.

So the strongest practical argument for automating step 3–4 — *"validation is a formality anyway,
because most of it cannot be run"* — **is weaker today than it was a week ago.** The checklist may
now actually be executable end to end for the first time.

🔴 This is stated as a fact, not as an objection, and it does not reverse the decision. It is
recorded here so that a later reader does not conclude the decision was taken while validation was
still impossible. **PROD's own Kong has never been probed** (s10 is unreachable from the operator
machine), so nothing here claims the equivalent for production.

### M9 — one thing gets strictly **better**.

Story 6.2 had to invent machinery for a problem that decision (b) deletes:

- `prod_tag` and `Deploy run id` written as `pending — dispatch not yet made`, because the row
  precedes the dispatch;
- a **superseding-row protocol** — *"every fact that arises after the dispatch … is carried by a new
  row that names the row it completes"* — for the run id, the deployed tag, the smoke-check outcome,
  a freeze-window break, a rollback.

Recording **after** the dispatch makes every one of those cells knowable at write time. The
`pending` values and the superseding-row protocol become **unnecessary** for the ordinary path.
Append-only stays (a correction is still a new row); what goes away is that the *normal* case needed
two rows.

## 3. Recommended Approach

**Selected: Option 1 — Direct Adjustment, hybrid mechanism.** Two new stories inside Epic 6, plus a
documentation pass applied directly as this proposal's own output. No rollback, no MVP review.

**Rejected: Option 2 (rollback).** Nothing needs reverting. Stories 5.4, 6.5, 6.6 and 6.7 all stay
as shipped; only text and one guard change.

**Rejected: Option 3 (MVP review).** No goal moves.

### For (a) — the PRE-PROD record

Move the record **into `deploy-preprod.yml` as a job gated on a successful deploy**, dropping the
`validated` input. Keep `record-preprod-candidate.yml` dispatchable — for backfill, and because
retiring a workflow that has ten green dispatches behind it buys nothing.

**Effort: Low. Risk: Low.** The mechanism exists and works; the change is deletion plus a `needs:`.

### For (b) — the production ledger

**Generate `docs/prod-releases.md` by query, and do not open a repository-write credential.**

M1 says the committed form is impossible; M2 says the query form is free. The generator is a small
script (`scripts/`, run by a human or by CI on a schedule) that reads `/actions/runs`, filters
`workflow_id == "deploy-prod.yml"` **by `event_payload` containing `inputs`, not by `event`** (M4),
and renders the table. The two human-only columns (`Waiver?`, `Note`) are carried in a small
side-file the generator merges by run id.

**Effort: Medium. Risk: Low** — nothing it does can affect a deploy; the worst failure is a stale
table, and the underlying `action_run` rows remain the source of truth.

**Open item to measure before implementation: `action_run` retention.** If Forgejo prunes those rows,
the query-derived ledger has a horizon. The generator's committed output is the archive, so a
periodic run bounds the exposure — but the retention figure must be measured, not assumed. Nothing
in this project has ever been allowed to rest on an unmeasured retention rule (`#d38` §9).

### 🔴 The decision this leaves to Oleg

M3 means the generated `Approved by` cell reads `platform-admin` — an account shared by Oleg and the
agent, which under the regulation's own rule is not an approval record.

- **(i) Accept it and rename the column** to `Dispatched by (account)`, dropping the claim of
  personal attribution. Cheap, honest, and matches "the dispatch IS the approval" literally: the
  ledger records *that a dispatch happened and by which account*, which is exactly and only what the
  instance knows.
- **(ii) Create a per-person Forgejo account for Oleg** and stop dispatching production through
  `platform-admin`. Restores the name. Costs an infrastructure change outside this repository — and
  would also stop the agent being able to dispatch production at all, which may be the point rather
  than the cost.

**Recommendation: (i) now, (ii) filed as deferred work owned by Oleg.** (i) is not a workaround for
(ii); it is the accurate description of what this instance can attest to, and it should be written
that way even if (ii) later happens.

### 4.10 `docs/production-approval-regulation.md` — four sections

#### `## What must be true before approval is sought`

**OLD**
> A candidate recorded in the PRE-PROD registry (`preprod-<sha>`), its `RVC-v1.1` Execution Log
> section written, and its row appended to `docs/preprod-candidates.md` — carrying its **derived**
> verdict and **any waiver**, both visible. **A derived verdict of `fail` with no waiver covering it
> is not approvable**; visibility is the precondition, not the permission.

**NEW**
> A candidate **deployed to PRE-PROD**, which mints `preprod-<sha>` automatically (`#d51`), its
> `RVC-v1.1` Execution Log section written, and its row appended to `docs/preprod-candidates.md` —
> carrying its **derived** verdict and **any waiver**, both visible. **A derived verdict of `fail`
> with no waiver covering it is not approvable**; visibility is the precondition, not the permission.
>
> 🔴 **AMENDED 2026-08-27.** Until this date the marker's *existence* implied a human had claimed
> `validated=pass`, because the recorder refused to run without a verdict. **It no longer does.** The
> marker is now written by the deploy itself, and **nothing in any workflow reads the verdict** —
> `RVC-v1.1` and its waiver are enforced by this rule alone. The sentence below (*"the approver reads
> `docs/preprod-candidates.md`, not only the registry tag"*) was already the rule; it is now the
> **only** thing standing between a `fail` verdict and a production release.

#### `## How the approval is recorded`

**OLD**
> One row in `docs/prod-releases.md`, **appended before the dispatch**, carrying the `image_tag` and
> the approver's **own start and end timestamps** — both mandatory, because this document's freeze
> window is defined over them …

**NEW**
> 🔴 **REWRITTEN 2026-08-27 (`#d51`) — the approval is no longer a row written before the dispatch.**
>
> **The dispatch of `deploy-prod.yml` IS the approval.** There is no act preceding it that a person
> performs in a file, and this document no longer claims there is. Whoever dispatches a production
> release has approved it, at the moment they dispatch it, and is bound by everything on this page.
>
> The ledger **records that dispatch after the fact**. `docs/prod-releases.md` is **generated from
> `action_run`**, not appended by hand: eight of its ten columns are already recorded by the instance
> and readable over the REST API without depending on a job log (which is why the file existed —
> six `log_in_storage=f` observations across Stories 5.3 and 5.4). The two that are not — `Waiver?`
> and `Note` — remain human, carried in a side-file keyed by run id.
>
> ⚠️ **What the ledger can and cannot attest, stated rather than left to be discovered.** Measured
> 2026-08-27 across all 717 runs in this repository: **`trigger_user` takes exactly two values,
> `platform-admin` (705) and `forgejo-actions` (12).** There is no per-person attribution on this
> instance. The `Approved by` column is therefore renamed **`Dispatched by (account)`** and **makes
> no claim about which person acted** — it cannot distinguish Oleg from the agent, both of which
> dispatch through the same admin account. The rule that an approver is a **name** is unchanged as a
> rule; the ledger simply stops pretending to record one. Restoring personal attribution requires a
> per-person Forgejo account and is deferred work owned by Oleg.

#### `## The freeze window`

**OLD**
> **… PROD's window will run from the approval row being appended to that smoke check passing** …

**NEW**
> **PROD's window runs from the `deploy-prod.yml` run's start to the smoke check's outcome**, and no
> other dispatch targets the PROD stand inside it. 🔴 **AMENDED 2026-08-27 (`#d51`): it used to start
> at the approval row being appended, and there is no longer such an append.** Both ends are now
> machine-recorded (`started`, and the smoke job's conclusion), which makes the window verifiable
> from the instance rather than from the approver's own honesty about when they began reading. **It
> still closes on that check's outcome whatever the outcome is** — a failed check, a failed deploy or
> a dispatch never made all end it. It still binds the s10 stand only. **Only Oleg may break it, and
> the break is recorded in the ledger** — in the human side-file, since a break is by definition not
> derivable from a run.

#### `## Who approves` — append

> 🔴 **AMENDED 2026-08-27 (`#d51`).** Oleg remains the only approver as a **rule**. What changed is
> that the rule is now **entirely unenforced by machinery, in both directions**: nothing checks who
> dispatches, and there is no longer even a file the approver must touch first. **The named cost
> in this section — "while Oleg is unavailable nothing can be approved" — is no longer technically
> true, and is now a policy statement only.** Anyone with repository write access can dispatch a
> release and the ledger will record it as `platform-admin`. Risk owner: Oleg, 2026-08-27.
