### 0.1. Побочная находка: баг в текущем GitHub CD

При пуше тега `v*` выражение в `CD.yml:122` вычисляет `environment: dev` (условие проверяет только `refs/heads/main`), а шаг `set-env` (`CD.yml:149`) в ветке `else` ставит `DEPLOY_ENV=production` и деплоит на прод. То есть required reviewers прод-окружения обходятся пушем тега. К миграции отношения не имеет — но это живой баг сегодня, чинить в текущем CD или закрыть переходом на dispatch-only (см. фазу 7).

#### Что установлено при разборе (07.08.2026, story 1.1)

- **Тегов `v*` в репозитории не было ни разу** — `git tag` пуст локально, `GET /repos/CRM-Prionex/fe-prionex/tags` возвращает `[]`. Тег-путь релиза не используется.
- **Гейт на `production` номинальный.** У окружения `production` нет ни одного правила защиты (`protection_rules: []`, `can_admins_bypass: true`). Required reviewers, которые «обходятся», в реальности не настроены — обходить нечего. То же у `dev` и `staging`.
- **Тег-путь падал, но прод всё равно затрагивался.** `BRANCH_NAME=$(echo "$GITHUB_REF" | sed 's/refs\/heads\///')` (`CD.yml:190`) на `refs/tags/v1.2.3` не срабатывает, `docker pull` получает невалидный тег и `exit 1` (`CD.yml:196`) отрабатывает **до** `docker compose down`. Но шаг scp (`CD.yml:154-162`) выполняется раньше и перезаписывает `docker-compose.server.yml` на прод-сервере. То есть запись на прод без апрува происходила, полного деплоя — нет. Защита здесь случайная: любая правка обработки имени тега превратила бы это в полноценный неапрувленный прод-деплой.
- **Зеркала Forgejo ↔ GitHub нет.** `main` совпадает (`e6ecfced`), но `development` разошёлся: Forgejo `372ee2c4`, GitHub `405db726` (коммит от 07.08.2026 12:52, он же запустил CD). Пуши идут в GitHub, Forgejo — отставшая копия. Локальный `origin` смотрит на Forgejo, remote на GitHub не настроен.

#### Решение и его статус

Обход закрывается **снятием триггера `v*`**, а не починкой выражения: тегами не пользуются, а починка выражения потребовала бы настроить required reviewers на `production`, то есть повесить апрув на **каждый** мерж в `main` — на ежедневный путь релиза — ради пути, которым никто не ходит. Пайплайн всё равно выводится из эксплуатации (фаза 7, декомиссия GitHub).

В коммите `09591984` ветки `fix/cd-close-tag-gate-bypass`:

- удалён триггер `tags: ['v*']` из `on.push` и клауза `startsWith(github.ref, 'refs/tags/v')` из `if:` деплой-джобы;
- выражение `environment`, его копия в Slack-payload и `set-env` сведены к одному дискриминатору (`refs/heads/development` → `dev`, иначе `production`), чтобы разойтись снова они не могли. На достижимых ref поведение не меняется — проверено перебором `main`, `development` и обоих вариантов `workflow_dispatch`.

> **Статус: на GitHub не доставлено.** По решению от 07.08.2026 GitHub не трогаем, поэтому правка живёт только в этом репозитории. `.github/workflows/CD.yml` действует исключительно на GitHub — значит **на живом GitHub CD обход остаётся открытым** до тех пор, пока там вообще возможно запустить CD. Наблюдаемая проверка (пуш тестового тега → прогон не создаётся) не проводилась по той же причине. Остаточный риск принят осознанно; практически он ограничен тем, что тегами никто не пользуется.

## 1. Блокеры, которые надо решить до написания workflow

Это не «сделать позже» — от решений здесь зависит структура пайплайна.

### 1.1. Артефакт нельзя промотировать PRE-PROD → PROD (критично)

Процесс требует: *«PROD receives the exact version validated in PRE-PROD»*, *«Rebuilding the application specifically for the production deployment is discouraged»*. Но сейчас `VITE_API_BASE_URL` / `VITE_WS_URL` запекаются в бандл на build (`CD.yml:110-112`), значит образ preprod физически не равен образу prod.

Варианты:

- **A (рекомендуется).** Ввести runtime-конфиг: `entrypoint.sh` в nginx-образе генерирует `/config.js` из env-переменных контейнера, `index.html` подключает его до бандла, код читает `window.__APP_CONFIG__` с fallback на `import.meta.env`. Один образ на все среды → честный промоушен и мгновенный rollback.
- **B (не дешевле A — см. ниже).** Перевести фронт на относительные пути, чтобы весь трафик шёл через фронтовый nginx.
- **C (компромисс на первую итерацию).** Мигрировать «как есть» с пересборкой под каждую среду, промоушен отложить в отдельную задачу. Тогда фаза 7 явно помечается как «принцип 5 не соблюдён».

**Про вариант B — важное уточнение.** Первоначальная оценка «переменные убираются сами собой, nginx уже всё проксирует» **неверна**. Фактически:

- 3 из 5 socket.io-хуков вызывают `io(WS_URL, {...})` **без** опции `path` — `useCallWebSocket.ts:74`, `useCallStateUpdates.ts:45`, `useIncomingCall.ts:36`. Дефолтный путь socket.io — `/socket.io/`, а `nginx.conf` проксирует только `/api/` и `/ws/`. Такой запрос попадёт в SPA-fallback `location /` и вернёт `index.html`;
- корректно настроены только `useDialerSocket.ts:47` (`path: '/ws/dialer'`) и `useNotificationSocket.ts:41` (`path: '/ws/notifications/socket.io'`);
- у всех хуков дефолт при пустой переменной — `http://localhost:8005` / `:8000`, то есть сборка «без переменных» даёт молча нерабочий бандл, а не относительные пути;
- сейчас `VITE_WS_URL` в проде указывает напрямую на `wss://api.crm-prionex.online`, минуя фронтовый nginx. Перевод на относительные пути меняет маршрут WS-трафика и требует сверки маршрутов Kong.

Итого вариант B = правка `path` у трёх хуков + снятие localhost-дефолтов + проверка Kong. По трудоёмкости сопоставимо с A, но A даёт ещё и гибкость по остальным переменным. **Рекомендация: A.**

> **Решение принято 07.08.2026: вариант C — вопреки рекомендации выше.** Мигрируем как есть, с пересборкой под каждую среду; промоушен артефакта PRE-PROD → PROD в эту миграцию не входит и записан как технический долг. См. [migration-decisions.md#d1](./migration-decisions.md#d1), последствия для гейта промоушена — [#d2](./migration-decisions.md#d2), объём работ по погашению долга (вариант A) — [#d3](./migration-decisions.md#d3).
>
> Разбор вариантов выше сохранён как обоснование этого решения.

### 1.2. DEV и PRE-PROD на одном хосте s1 конфликтуют

Три конфликта в текущих конфигах:

- `container_name: fe-prionex` и `name: fe-prionex` (`docker-compose.server.yml:4,9`) — жёстко заданы, два стенда не поднимутся;
- порт `8080` захардкожен по умолчанию — нужен разный `FRONTEND_PORT`;
- **главное:** сеть `crm-network` внешняя и общая, nginx резолвит `crm-kong-gateway` по имени → preprod-фронт уедет на dev-бэкенд.

Нужно: параметризовать имена (`COMPOSE_PROJECT_NAME`, `CONTAINER_NAME`), развести каталоги (`~/crm-prionex/fe-prionex-dev` / `-preprod`), и **согласовать с бэкендом отдельную сеть `crm-network-preprod` с собственным Kong**. Без второго Kong-стенда на s1 preprod получается фиктивным.

Сюда же — хардкоды в healthcheck-шаге, который портируется из CD: `docker inspect ... fe-prionex` (`CD.yml:224`) и `curl localhost:8080` (`CD.yml:233`). При трёх стендах с разными именами и портами копирование «как есть» даст зелёный healthcheck на мёртвом стенде. Оба места параметризовать вместе с compose.

### 1.3. В Forgejo нет GitHub Environments с обязательным апрувом

`environment: name: production` (`CD.yml:121-122`) с required reviewers в Forgejo не воспроизводится.

**Прямо: технического гейта на PROD не будет.** В Forgejo нет прав на уровне отдельного workflow — любой с write-доступом к репозиторию может запустить `deploy-prod.yml` через `workflow_dispatch`. Барьеры остаются организационные (апрув фиксируется в трекере) плюс один технический — guard промоушена из фазы 7. Это надо принять осознанно и записать в регламент.

### Фаза 3 — CI на Forgejo (параллельно с GitHub)

1. Создать `.forgejo/workflows/ci.yml` — портирование `CI.yml`: те же 4 job'а, те же скрипты `npm run lint / format:check / typecheck / test:run / build`, метка `node-20`.
2. Убрать codecov; coverage — в артефакт.
3. Триггеры: `pull_request` на `main` + `push` в feature-ветки.
4. Прогон на 5+ реальных PR в Forgejo.
5. Включить required status checks на `main`. **Обязательное условие: к этому моменту работают два runner'а** — иначе упавший единственный runner замораживает все мержи.

**DoD (проверяемый):** 5 подряд зелёных CI-прогонов на реальных PR; время полного прогона ≤ 15 минут; прямой push в `main` отклоняется.
Прямое сравнение «Forgejo CI vs GitHub CI на одном PR» из плана убрано — PR не зеркалируются между платформами, сравнить один и тот же PR технически нельзя. Сравнение времени — по прогонам на общих ветках, если зеркалирование push'ей настроено (см. фазу 0.4).
**Rollback:** снять required checks, GitHub CI остаётся источником истины.

### Фаза 4 — Сборка и публикация образа

1. `.forgejo/workflows/build.yml` на метке `docker-build`: checkout → buildx → login в Forgejo registry → metadata → build & push.
2. **Триггеры — включая feature-ветки:** `push` в `main`, tag `v*`, `push` в feature-ветки (или `workflow_dispatch` с `ref`). Иначе деплой feature-ветки на DEV невозможен: `deploy-dev.yml` делает fail-fast `docker pull` и падает, потому что образа просто нет.
3. Схема тегов: `sha-<short>` (всегда), `<branch>`, `v*` из git-тега, `latest` только с `main`.
4. Кэш — `type=registry`.
5. Build-args — по решению из п.1.1.
6. `concurrency: cd-${{ github.ref }}`, `cancel-in-progress: false` — сохранить поведение `CD.yml:19-21`. **Плюс обязательный fallback:** `flock` на файл в каталоге стенда внутри деплой-скрипта. Если инстанс Forgejo игнорирует `concurrency` (см. фазу 0.3), ошибки не будет — просто два деплоя параллельно погонят `down`/`up` на одном стенде. Серверный lock от версии Forgejo не зависит.

**DoD:** push в любую ветку даёт неизменяемый образ `sha-<short>`, привязанный к коммиту (принцип 6); два одновременных деплоя на один стенд сериализуются (проверить намеренно).

### Фаза 5 — DEV на s1 (новый стенд, старый не трогаем)

1. Поднять **параллельный** стенд на s1: каталог `~/crm-prionex/fe-prionex-dev/`, порт `8082`, отдельный `container_name`.
2. `deploy-dev.yml`: `workflow_dispatch` с input `ref` — любой разработчик деплоит свою feature-ветку без апрува (требование документа к DEV). Зависит от фазы 4.2.
3. Шаги деплоя портируются из `CD.yml:154-238`: scp compose → `docker compose down` → `pull` (fail-fast без fallback на `latest` — важное свойство, сохранить) → `up -d` → healthcheck по `docker inspect .State.Health.Status` с **параметризованными** именем контейнера и портом (п.1.2). SSH/SCP — нативные, не appleboy (п.1.4).
4. Отдельная задача (может идти параллельно): еженедельный сброс DEV к `main` — `schedule`-workflow по воскресеньям, деплой `main` + `docker image prune`.
5. Прогон: 5+ деплоев разных feature-веток.

**DoD:** деплой feature-ветки на DEV занимает < 10 минут, старый dev-стенд не затронут.
**Cutover DEV:** после недели параллельной работы — переключить DNS/порт на новый стенд, старый оставить остановленным на 2 недели.

### Фаза 6 — PRE-PROD на s1 (новая среда)

1. Инфра: каталог `~/crm-prionex/fe-prionex-preprod/`, порт `8081`, сеть и Kong из п.1.2, домен + TLS.
2. `deploy-preprod.yml`: **только** `workflow_dispatch` с обязательным input `image_tag` (конкретный `sha-` или `v*`). Никаких автотриггеров.
3. **Фиксация релиз-кандидата — ретегом в registry, не файлом на сервере.** После успешного деплоя workflow создаёт тег `preprod-current` (`docker buildx imagetools create -t .../fe-prionex:preprod-current .../fe-prionex:<image_tag>`) и `preprod-<sha>`. Реестр становится единственным источником истины: история тегов = история релизов, состояние не размазано по серверам, и это же даёт основу для промоушена в фазе 7.
   *(Первоначальный вариант — файл `RELEASE` на preprod-сервере — отброшен: он хранит один слот, из-за чего guard в фазе 7 блокировал бы откат на предыдущую версию.)*
4. Место под E2E: job `e2e` после healthcheck. Сейчас в проекте E2E нет (`package.json` — только vitest), поэтому на первом этапе — заглушка + чек-лист ручной валидации критичных флоу. Автотесты — отдельная задача.
5. Прогон полного релизного цикла на «пустом» релизе.

**DoD:** релиз-кандидат разворачивается на PRE-PROD по тегу, в реестре появляются `preprod-current` и `preprod-<sha>`.

**Про заморозку scope:** ничто технически не мешает задеплоить в preprod новый тег посреди валидации. Заморозка релиза — **процессная договорённость, не техническая гарантия**. В DoD не выносится.

### Фаза 7 — PROD на s2 (переключение)

Делается последним, после того как фазы 3-6 отработали на реальном релизе.

1. `deploy-prod.yml`: `workflow_dispatch`, input `image_tag` + опциональный `rollback: bool`.
2. **Guard промоушена по реестру, а не по серверу:** проверить, что `image_tag` существует в registry с меткой `preprod-*` (то есть образ действительно проходил PRE-PROD). Это техническое воплощение принципа «в PROD едет ровно то, что прошло PRE-PROD». При `rollback: true` guard пропускается — откат на любой ранее задеплоенный прод-тег должен быть возможен всегда.
3. Никакой сборки в этом workflow — `docker pull` существующего тега + ретег в `prod-current`. Требует решённого п.1.1; при варианте C здесь остаётся пересборка, и это явно помечается как временный компромисс.
4. Смоук-чек после деплоя: доступность, `docker inspect` health, `curl` критичных путей, проверка логов на ERROR за последние 5 минут.
5. Slack-уведомления — start / success / failed через `curl`.
6. **Переключение (cutover).** Текущий прод-образ лежит в ghcr, а не в Forgejo registry, поэтому «no-op деплой того же образа» требует подготовки:
   1. спуллить работающий прод-образ из ghcr, запушить его в Forgejo registry под `sha-<коммит>` и `prod-current`;
   2. прогнать `deploy-prod.yml` с `rollback: true` на этом теге — проверка всей механики без смены содержимого;
   3. убедиться, что стенд жив, и только следующий реальный релиз вести через полный цикл Forgejo.

**DoD:** релиз выехал через Forgejo; откат на предыдущий тег выполнен и проверен на практике (не в теории).
**Rollback:** `deploy-prod.yml` с предыдущим `image_tag` и `rollback: true` — время отката = `docker pull` + рестарт.

### Фаза 8 — Отключение GitHub

1. 1-2 релизных цикла — оба пайплайна живы, GitHub Actions в режиме «только CI, без деплоя» (отключить job `deploy` в `CD.yml`).
2. Отключить workflow в GitHub, удалить деплой-секреты (SSH-ключи!), отозвать ghcr-токены.
3. Удалить `.github/workflows/`, обновить `README.md` и документ Deployment Process (добавить PRE-PROD, s1/s2, схему тегов, регламент апрува PROD из п.1.3).
4. Отдельно: ротация SSH-ключей, которые лежали в GitHub Secrets.

| `concurrency` молча игнорируется версией Forgejo | риск не реализовался — probe-тест на `v15.0.5` подтвердил очередь и отмену ([migration-decisions.md#d8](./migration-decisions.md#d8)); митигация сохраняется: `flock` на сервере (фаза 4.6), поскольку concurrency остаётся best-effort — не зависит от версии |
| PRE-PROD без своего Kong = фиктивная валидация | Блокер 1.2, согласовать с инфрой в фазе 0 |
| Промоушен образа невозможен без п.1.1 | Выбран вариант C; компромисс задокументирован — [migration-decisions.md#d1](./migration-decisions.md#d1), [#d3](./migration-decisions.md#d3) |

| Оба пайплайна одновременно деплоят на один стенд | В фазах 3-6 Forgejo деплоит **только** на новые стенды; job `deploy` в GitHub CD отключается в начале фазы 7 |

| Push на `main`/`staging`/`development` попадает в legacy `.github/workflows/CD.yml` на чужом раннере и деплоит на PROD | Деплой не состоялся: Story 1.13 положила `.forgejo/workflows/` на все три ветки и доказала тестом отсутствие рана на каждой ([#d8](./migration-decisions.md#d8) — исходная находка, [#d9](./migration-decisions.md#d9) — нейтрализация). ## 7. Что осознанно не делаем

- **Файл `RELEASE` на сервере как источник истины** — заменён на теги в реестре (фаза 6.3): один слот ломал откат.
- **Метка runner'а `ubuntu-latest`** «чтобы не править `runs-on`» — мотивация ложная, workflow всё равно пишутся с нуля. Явные метки `node-20` / `docker-build` понятнее и решают проблему сборки образа.
- **Порты как CI-переменные** — дублирование состояния, уже есть в серверных `.env`.
- **codecov** — убран из CI, coverage остаётся артефактом.
- **Технический гейт апрува PROD** — в Forgejo невозможен (п.1.3), заменён процессным.
- **Промоушен артефакта PRE-PROD → PROD** — по решению от 07.08.2026 выбран вариант C (п.1.1): образ пересобирается под каждую среду, в PROD едет пересборка коммита, а не проверенный на PRE-PROD артефакт. Принцип *«PROD receives the exact version validated in PRE-PROD»* нарушен осознанно и записан как технический долг — [migration-decisions.md#d1](./migration-decisions.md#d1), объём погашения — [#d3](./migration-decisions.md#d3).
