## D1. Блокер 1.1 — вариант C: образ собирается под каждую среду

**Решение.** Приложение мигрирует **как есть**. Переменные Vite остаются вшитыми в бандл на
этапе сборки. Из этого следуют три вещи, каждая из которых принята осознанно:

1. **Контракт сборки не меняется.** `Dockerfile.prod:19-22` сохраняет
   `ARG VITE_API_BASE_URL` / `ARG VITE_WS_URL` → `ENV` → `npm run build`. Слой
   runtime-конфигурации (`entrypoint.sh`, генерирующий `/config.js`) **не вводится**.
2. **Под каждую среду собирается отдельный образ.** Один коммит порождает до трёх разных
   образов — `dev`, `preprod`, `prod`, — физически различных между собой. Поэтому теги обязаны
   нести дискриминатор среды (например, `sha-<short>-prod`); конкретная схема тегов
   определяется в stories 3.2 и 3.3, здесь фиксируется только необходимость дискриминатора.
3. **В PROD едет не тот артефакт, который валидировался на PRE-PROD.** В PROD едет пересборка
   того же коммита.

**Какой принцип этим нарушен.** Дословно, из документа Deployment Process:

> *«PROD receives the exact version validated in PRE-PROD»*

и связанное с ним:

> *«Rebuilding the application specifically for the production deployment is discouraged»*

Оба нарушаются вариантом C сознательно. Это не упущение и не то, что «дойдут руки поправить по
ходу» — это условие, на котором миграция вообще стартует.

**Почему C, а не A и не B.**

- **A (runtime-конфиг)** — целевой вариант и рекомендация плана: один образ на все среды,
  честный промоушен, мгновенный откат. Но это правка приложения, а не пайплайна, и она
  блокирует старт миграции. Оставлена как долг — см. [D3](#d3).
- **B (относительные пути)** — при пересмотре оказался **не дешевле A**. Три из пяти
  socket.io-хуков вызывают `io(WS_URL, {…})` **без** опции `path`
  (`useCallWebSocket.ts`, `useCallStateUpdates.ts`, `useIncomingCall.ts`), а `nginx.conf:37-56`
  проксирует только `/api/` и `/ws/`; запрос по дефолтному `/socket.io/` уедет в SPA-fallback и
  вернёт `index.html`. Плюс `VITE_WS_URL` в проде сейчас указывает напрямую на
  `wss://api.crm-prionex.online`, минуя фронтовый nginx, — перевод на относительные пути меняет
  маршрут WS-трафика и требует сверки маршрутов Kong.
- **C** — компромисс первой итерации: миграция не ждёт правок приложения, а цена компромисса
  записана здесь и отслеживается.

**Статус долга.** Вариант C — **принятый и отслеживаемый технический долг** (NFR11), а не
закрытое решение. Пока долг не погашен, каждое требование, которое опиралось бы на единый
промотируемый артефакт, помечено в `epics.md` как `[C]`.

**Разбор вариантов:** [forgejo-migration.md §1.1](./forgejo-migration.md#11-артефакт-нельзя-промотировать-pre-prod--prod-критично).

## D2. Гейт промоушена доказывает идентичность коммита, а не образа

**Статус: спроектировано, не реализовано — обновить в story 6.5.**

**Решение.** `deploy-prod.yml` перед релизным деплоем извлекает SHA коммита из `image_tag` и
проверяет, что в реестре существует тег `preprod-<sha>`. Если тега нет — деплой отклоняется до
того, как что-либо будет сделано с s2.

**Что этот гейт доказывает.** Что **коммит** проходил валидацию на PRE-PROD.

**Чего он доказать не может.** Что её проходил **образ**. Под вариантом C ([D1](#d1))
prod-образ — это отдельная сборка, побайтово отличная от preprod-образа. Проверить
идентичность артефакта нечем: сравнивать нечего.

**Остаточный риск, который отсюда следует.** В PROD может приехать непроверенным всё, что
различается между двумя сборками одного коммита:

- значения build-time переменных (`VITE_API_BASE_URL`, `VITE_WS_URL` и остальные из [D3](#d3)) —
  опечатка в prod-переменной не будет поймана валидацией на PRE-PROD;
- окружение сборки — версия базового образа, состояние кэша;
- транзитивно разрешённые зависимости, если сборки разнесены во времени.

Формулируя коротко: **зелёная валидация на PRE-PROD — это свидетельство об исходном коде, а не
о байтах, которые поедут в прод.**

**Откат.** При `rollback: true` гейт пропускается — намеренно: вернуться на любой ранее
задеплоенный prod-тег должно быть возможно всегда, в том числе когда `preprod-<sha>` уже
удалён ретеншеном.

**Требования:** FR16, и story 6.5, которая этот гейт реализует и обновляет эту запись.

## D3. Технический долг: переход на вариант A (runtime-конфиг)

**Статус: открыто. Владелец не назначен, срок не назначен.** План миграции этот долг не
погашает и не планирует — здесь зафиксировано только его содержание и объём, чтобы решение
принималось по фактам, а не по памяти.

**Что нужно сделать.** `entrypoint.sh` в nginx-стадии образа генерирует `/config.js` из
переменных окружения контейнера; `index.html` подключает его до бандла; код читает
`window.__APP_CONFIG__` с fallback на `import.meta.env`. Результат — **один образ на все
среды**, честный промоушен PRE-PROD → PROD и откат без пересборки. Гейт из [D2](#d2) при этом
становится проверкой идентичности артефакта, а не коммита.

**Объём работ — по факту в коде, а не по оценке плана.** План называет две переменные; в коде
их четыре (проверено на `54c6faae`):

| Переменная | Места использования | Примечание |
|---|---|---|
| `VITE_API_BASE_URL` | `src/lib/api.ts:5`, `src/features/calls/api/callService.ts:16`, `src/features/dialer/api/dialerHttpService.ts:17`, `src/features/auth/hooks/useTabTracker.ts:153` | передаётся как `--build-arg` сегодня |
| `VITE_WS_URL` | `src/features/calls/hooks/useCallWebSocket.ts:14`, `useCallStateUpdates.ts:13`, `useIncomingCall.ts:8`, `src/features/dialer/hooks/useDialerSocket.ts:9`, `src/features/notifications/hooks/useNotificationSocket.ts:8` | передаётся как `--build-arg` сегодня |
| `VITE_OPERATOR_PHONE_URL` | `src/features/operatorPhone/constants.ts:9` | **`CD.yml` её не передаёт** |
| `VITE_EASYPAY_PORTAL_API_KEY` | `src/features/easypay/api/easypayApi.ts:25` | **`CD.yml` её не передаёт** |

`VITE_BUILD_TS` в этот список **не входит**: она подставляется через `define` в
`vite.config.ts:8` из `Date.now()` на этапе сборки, а не из окружения. Плюмбинг runtime-конфига
её не касается.

**Что в этой работе неочевидно:**

- **Localhost-дефолты придётся снимать одновременно.** Каждое место чтения переменной сейчас
  написано по шаблону «если не задана — подставить локальный адрес»
  (`'http://localhost:8005'` в трёх call-хуках и в `useNotificationSocket.ts:8`,
  `'http://localhost:8000'` в `useDialerSocket.ts:9`,
  `'http://localhost:5173'` в `operatorPhone/constants.ts:5`, `?? ''` в `easypayApi.ts:25`).
  Пока эти дефолты на месте, отсутствующая переменная не роняет сборку, а молча даёт
  нерабочий бандл. NFR8 требует обратного — падать громко.
- **Тесты стабят окружение.** `src/test/setup.ts:11` подменяет `VITE_API_BASE_URL` через
  `vi.stubEnv`. Для `window.__APP_CONFIG__` понадобится параллельный механизм, иначе тесты
  начнут читать не то, что читает приложение.
- **`docker-compose.server.yml` получит per-stand переменные**, которые образ больше не несёт
  в себе. Сейчас файл ничего подобного не прокидывает.

**Отдельная находка, к варианту C отношения не имеющая.** `CD.yml:110-112` передаёт в сборку
только две переменные из четырёх. Значит `VITE_OPERATOR_PHONE_URL` и
`VITE_EASYPAY_PORTAL_API_KEY` **сегодня в проде разрешаются в свои in-code дефолты** —
`http://localhost:5173` и пустую строку соответственно, — хотя обе объявлены в
`.env.example:39,73`. Это существующий дефект, а не следствие варианта C. Чинится в story 3.3,
которая владеет build-args и правилом «никаких молчаливых дефолтов» (NFR8).

## D4. Блокер 1.2 — параметризация стендов и отдельная сеть PRE-PROD

**Решение.** DEV и PRE-PROD живут на одном хосте s1 и разводятся параметризацией:

- `COMPOSE_PROJECT_NAME`, `CONTAINER_NAME`, `FRONTEND_PORT` вместо захардкоженных значений —
  сейчас `name: fe-prionex` (`docker-compose.server.yml:4`),
  `container_name: fe-prionex` (`:9`) и порт по умолчанию `8080` (`:11`) не дают двум стендам
  подняться рядом;
- каталоги разведены: `~/crm-prionex/fe-prionex-dev/` и `~/crm-prionex/fe-prionex-preprod/`;
- порты: DEV — `8082`, PRE-PROD — `8081`, легаси-стенд остаётся на `8080` нетронутым;
- PRE-PROD получает **собственную сеть `crm-network-preprod` и собственный экземпляр Kong**.

**Последствие, если сетью пренебречь.** `nginx.conf:37-56` резолвит `crm-kong-gateway` по имени
внутри общей сети `crm-network`. В общей сети фронтенд PRE-PROD молча уедет на бэкенд DEV, и
валидация релиз-кандидата станет фиктивной — зелёной и ничего не значащей.

Туда же относятся хардкоды в healthcheck-шаге, портируемом из `CD.yml` (`docker inspect …
fe-prionex` и `curl localhost:8080`): при трёх стендах копирование «как есть» даёт зелёный
healthcheck на мёртвом стенде. Параметризуются вместе с compose.

**Внешняя зависимость.** Сеть и второй Kong на s1 предоставляет команда бэкенда/инфры — это
блокер на Epic 5, зафиксированный в story 1.6.

**Требования:** FR25, FR26, FR27, FR20.

## D5. Блокер 1.3 — технического гейта апрува PROD не будет

**Решение.** В Forgejo нет аналога GitHub Environments с required reviewers и нет прав на
уровне отдельного workflow. Любой участник с write-доступом к репозиторию может запустить
`deploy-prod.yml` через `workflow_dispatch`. Технического барьера на прод-деплой **не будет**,
и это принято, а не отложено.

**Что остаётся вместо него:**

- **организационный контроль** — апрув фиксируется в трекере, правило пишется в регламент
  (story 6.2) и в документацию процесса (story 7.3);
- **один технический барьер** — гейт промоушена из [D2](#d2), с оговоркой, что он проверяет
  коммит, а не артефакт.

**Требования:** NFR9.

## D6. Перенос секретов и переменных

**Решение.** Карта переноса зафиксирована в
[forgejo-migration.md §3](./forgejo-migration.md#3-перенос-секретов-и-переменных):

| GitHub | Forgejo | Уровень | Комментарий |
|---|---|---|---|
| `GITHUB_TOKEN` (ghcr) | `REGISTRY_TOKEN` | org | новый токен техпользователя `ci-bot`, право `write:package` |
| `DEV_SSH_HOST` / `USER` / `KEY` | `S1_SSH_HOST` / `USER` / `KEY` | repo | s1, общий для DEV и PRE-PROD |
| `PROD_SSH_HOST` / `USER` / `KEY` | `S2_SSH_HOST` / `USER` / `KEY` | repo | s2, **новый ключ** |
| `SLACK_CD_WEBHOOK_URL` | `SLACK_CD_WEBHOOK_URL` | org | без изменений |

Сопутствующие решения:

- **На s1/s2 — только `read:package`.** Право `write:package` держит исключительно `ci-bot`
  (NFR6).
- **Старый ключ s2 не отзывается** до завершения фазы 8 — иначе есть шанс потерять доступ к
  прод-серверу (NFR7).
- **Порты в CI-переменные не выносятся** — они уже живут в серверных `.env` каждого стенда,
  дублировать состояние незачем.
- **Fallback-значения URL из шага `set-api-url` (`CD.yml:40-77`) при переносе убираются.** Молчаливый дефолт на
  прод-API — мина: отсутствующая переменная должна ронять сборку, а не отгружать бандл,
  смотрящий не туда (NFR8).
- **Под вариант C нужны `_PREPROD`-переменные.** `VITE_API_BASE_URL_PREPROD` и
  `VITE_WS_URL_PREPROD` добавляются рядом с существующими парами `_DEV` / `_PROD` — третья
  среда появляется именно из-за [D1](#d1).

**Уточнение по типу.** `CD.yml` читает URL-переменные через контекст `secrets.`, тогда как
`epics.md` называет их repo *variables*. Чем они станут в Forgejo — секретами или переменными —
решается в story 1.12; URL бэкенда не является секретом, он и так виден в бандле.

> ⚠️ **Читать вместе с [D15](#d15) (13.08.2026).** Три строки этой карты больше не описывают
> реальность: `REGISTRY_TOKEN`/`ci-bot` заменены платформенными именами ([D14](#d14)),
> `S1_SSH_*`/`S2_SSH_*` удалены амендментом FR19 от 11.08, а пары `VITE_*` не создаются в Forgejo
> вообще — значения живут в `secret/fe/{dev,pre-prod,prod}/app`. На вопрос «секретами или
> переменными» ответ: ни тем, ни другим.

## D7. 07.08.2026 — на стороне GitHub не выполняется никаких действий

**Решение.** Этот план не выполняет **никаких** действий на GitHub: ни с workflow, ни с
настройками, ни с секретами, ни с учётными данными, ни с его container registry. GitHub
остаётся работать ровно так, как работает сегодня. Перенос доставки и контента на Forgejo —
задача, которой владеет Oleg, и она ведётся вне этого плана.

**Что из этого следует.**

- **Отменены шесть stories** — каждая требовала действия на стороне GitHub: 1.1 (закрыть обход
  прод-гейта пушем тега), 1.4 (модель синхронизации GitHub ↔ Forgejo), 1.5 (переходный
  регламент легаси DEV-стенда), 6.1 (отключить job `deploy` в GitHub CD), 7.1 (два релизных
  цикла с GitHub в режиме «только CI»), 7.4 (отозвать деплой-секреты и ghcr-токены). Номера
  здесь — **номера stories**, не пунктов этого плана: блокер 1.1 (вариант C, [D1](#d1)) и
  story 1.1 — разные вещи.
- **Обход гейта тегом остаётся открытым на живом GitHub CD.** Правка есть в репозитории
  (коммит `09591984`), но `.github/workflows/CD.yml` действует только на GitHub, куда она не
  доставлена. Подробности — [§0.1 плана](./forgejo-migration.md#01-побочная-находка-баг-в-текущем-github-cd).
- **В прод могут деплоить два пайплайна.** Легаси GitHub CD деплоит на s2 при мерже в `main` и

## D8. Возможности Forgejo Actions установлены по факту: версия, concurrency, workflow_call, composite actions

**Решение.** Story 1.3 подняла одноразовый probe-раннер (capacity 2, на рабочей станции, не на
s1/s2) и прогнала пять проб на throwaway-ветке `probe/forgejo-capabilities` против

установлен тестом, а не по документации релиза.

**Самая существенная находка — не про Actions, а про риск для PROD.** В организации `CRM`
уже зарегистрированы два раннера: `ci-hub` (метка `ubuntu-latest`, статус `idle`) и
`s1-build-crm` (метки `s1`, `ci`, `build-crm`). Пока `.forgejo/workflows/` в `main` не
существует, Forgejo резолвит директорию воркфлоу как `.forgejo/workflows` → `.gitea/workflows`
→ `.github/workflows` и падает на последний. Любой push `main` или `development` в Forgejo
**немедленно**, не в очередь, запускает `.github/workflows/CD.yml` на `ci-hub` — а его job
`deploy` делает `docker compose down/up` на **s2 PROD**. Митигация: `main`/`development` не
пушить в Forgejo, пока Story 2.1 не положит `.forgejo/workflows/`, либо пока
`.github/workflows/` не будет нейтрализован на стороне Forgejo. Именно поэтому сама story 1.3
работала через `probe/forgejo-capabilities`, а не через `main`.

**Версия и `[actions] ENABLED`.** `GET /api/forgejo/v1/version` → `15.0.5+gitea-1.22.0` (ветка
v15 LTS). `has_actions: true` на `CRM/fe-prionex` — косвенное подтверждение; прямое
доказательство — первый успешно выполнившийся пробный ран:
https://git.crm-prionex.com/CRM/fe-prionex/actions/runs/3 (`probe-smoke`,
`actions/checkout@v6`, статус success).

**Concurrency — очередь подтверждена тестом, определённое «да».** Probe A (без `concurrency`,
два параллельных `workflow_dispatch`) доказала capacity ≥ 2: оба рана стартовали и завершились
в одну и ту же секунду (started/stopped `20:26:18` / `20:27:20`, runs

единственное объяснение — очередь по группе `concurrency`, а не ожидание слота.
**AC2 = да.**

**Отмена (`cancel-in-progress: true`) — тоже да.** Probe B′ (группа `probe-cc2`): run #1 (run
[8](https://git.crm-prionex.com/CRM/fe-prionex/actions/runs/8)) создан/стартован/остановлен в

[9](https://git.crm-prionex.com/CRM/fe-prionex/actions/runs/9)). Это независимое подтверждение
B="да": ограничение по capacity никогда не *отменяет* выполняющийся джоб, только ставит в

сценарий «B=нет, но B′ отменяет» (флаг `CONCURRENCY_GROUP_QUEUE_ENABLED` выключен админом при
работающей версии) здесь не применим.

продовых `ci-hub`/`s1-build-crm` (риск «работает на пробном раннере, но не на v13» из Dev Notes
снят).

**Composite actions — да, подтверждено выполнением, а не только резолвом.** Первая попытка (run
[11](https://git.crm-prionex.com/CRM/fe-prionex/actions/runs/11)) упала — но не из-за отсутствия

`needs:`.

**AC3 — вывод про `flock` в Epic 4.** Concurrency честно отработал во всех пробах (B и B′), но

## D9. `.forgejo/workflows/` нейтрализует legacy-fallback — доказано на всех трёх ветках

**Решение.** Story 1.13 положила инертный `.forgejo/workflows/README.md` на все три ветки,
которые Forgejo резолвит как CD-triggering — `staging`, `development`, `main` — и доказала тестом
на каждой, что после этого push не создаёт ни одного Actions-рана. Это закрывает находку,
записанную первой в [D8](#d8): что незащищённый push на любую из этих веток немедленно исполняет
`.github/workflows/CD.yml` на чужом раннере `ci-hub` и деплоит.

**Механизм.** Forgejo резолвит директорию воркфлоу как `.forgejo/workflows` →
`.gitea/workflows` → `.github/workflows`, **первое совпадение побеждает** — выбирается первый
**существующий tree-entry**, независимо от того, есть ли в нём воркфлоу-файлы. На стороне GitHub
не меняется ничего: GitHub директорию `.forgejo/` полностью игнорирует, [D7](#d7) не нарушается.

**Что положено.** `.forgejo/workflows/README.md` — не воркфлоу, обычный markdown-файл,
Forgejo парсит только `.yml`/`.yaml`. Инертен по конструкции: директория существует, но не
содержит ничего исполнимого.

**Легаси-воркфлоу различаются по веткам — предыдущие формулировки были неполны.** До этой истории
change proposal (`_bmad-output/planning-artifacts/sprint-change-proposal-2026-08-07-runners.md`
§2, строки 129-130) обосновывал безопасность **пробной ветки** Story 1.3 тем, что «`CD.yml:4`
filters `[main, development]`» — утверждение верно только для локального `main`, и как общее
правило про ветки инстанса не работает. Отдельно: **сама [D8](#d8) занижает охват опасности** —
там записано «Любой push `main` **или** `development`», тогда как `staging` на своей же ветке
тоже CD-деплоящая. D8 не переписывается (правило append-only); её митигация («`main`/`development`
не пушить в Forgejo, пока Story 2.1 не положит `.forgejo/workflows/`») настоящей записью
**снята — исполнена**. Проверка `git show <ref>:.github/workflows/CD.yml` на всех трёх
Forgejo-ссылках:

| Forgejo ref | `CD.yml` push-ветки | `v*` теги | `workflow_dispatch` | `deploy.if` допускает | Deploy-секреты |

| `main` | `[main, development]` | да | да, `environment` по умолчанию `production` | main, development, `refs/tags/v*` | `PROD_SSH_*` / `DEV_SSH_*` |

Значит **из событий, которые может вызвать обычный git-push, CD-свободно только `pull_request`**:
ни один `CD.yml` не имеет триггера `pull_request`. Контроль и тест в Story 1.13 прошли через PR, а
не push ветки. ⚠️ **Но `pull_request` — не единственное CD-свободное событие в абсолютном

есть на этом инстансе он заведомо работает. В исходном планировании Story 1.13 этот триггер не

**Решение.** Раннер зарегистрирован на **s1**, **на уровне репозитория** (`CRM/fe-prionex`, не

(`ci-hub`, `s1-build-crm`, `s1-deploy-dev-preprod`), always-on, доступ по SSH подтверждён.

**Адресация s1.** В рамках этой story хост использовался по внутреннему адресу `10.67.0.1`
(SSH по ключу). Это тот же хост, что во всех остальных артефактах записан как **`72.62.17.132`** —
внешний адрес. Оба адреса указывают на s1; расхождение зафиксировано здесь, чтобы следующая story

**Имя и версия.** `s1-fe-prionex-1` (следующий по 1.9 будет `-2`), `forgejo-runner` **v13.0.0**,

**Метки — обе, дословно с `docker://`-суффиксами:** `node-20:docker://node:20-bookworm`,
`docker-build:docker://code.forgejo.org/oci/docker:cli`. Голая метка `docker-build` **не** host-режим

**Docker-доступ: Docker-in-Docker, не хостовый сокет.** Story предполагала «Recommended: host binary +
systemd, `container.docker_host: automount`» — от этого плана пришлось отказаться: у s1 действует
недокументированное в этой story, но обязательное на этом хабе правило **AD-6** («хостовый
`docker.sock` не монтируется ни в один сервис, никогда») — на shared production hub утечка сокета
означала бы доступ джобы к OpenBao и к контейнерам стороннего арендатора (`techno-finance`). Вместо
этого — паттерн, уже принятый всеми существующими runner-проектами хаба: выделенный сайдкар
`dind` (`docker:27.5.1-dind`, privileged, `dockerd -H tcp://0.0.0.0:2375 --tls=false`, без unix-сокета
вообще), `runner` обращается к нему только по TCP (`container.docker_host: tcp://dind:2375`).
`container.options: -e DOCKER_HOST=tcp://172.17.0.1:2375` — это адрес шлюза **вложенного** докера
изнутри job-контейнера, а не хостовый путь; тот же приём, что в примере апстрима.

🔴 **AD-6 в исходной формулировке неверно — установлено прямым осмотром хоста 11.08.2026
(code review). Решение в пользу DinD от этого не меняется, но обоснование меняется.**

Исходный текст утверждал два факта, ни один из которых не выдержал проверки: что runner-проектов на
s1 четыре (в другом месте записи — «три»), и что хостовый `docker.sock` «не монтируется ни в один
сервис, никогда, подтверждено против всех четырёх».

Что на хосте на самом деле (`ls -1d /opt/forgejo*`, `docker inspect` по всем работающим
контейнерам):

| Проект | Механизм | Хостовой `docker.sock` |
|---|---|---|
| `/opt/forgejo-runner` | dind, `docker_host: tcp://dind:2375` | нет |
| `/opt/forgejo-runner-ci` | dind, `docker_host: tcp://dind:2375` | нет |
| `/opt/forgejo-runner-crm` | dind, `docker_host: tcp://dind:2375` | нет |
| `/opt/forgejo-runner-telecom` | dind, `docker_host: tcp://dind:2375` | нет |
| `/opt/forgejo-runner-deploy` | **хостовый сокет**, `docker_host: ""` | **да** |
| `/opt/forgejo-runner-fe-prionex` (наш) | dind, `docker_host: tcp://dind:2375` | нет |

То есть runner-проектов **шесть**, пять из них чужие (плюс сам `/opt/forgejo` — инстанс Forgejo).
И **исключение из AD-6 существует и задокументировано его же авторами**: `forgejo-runner-deploy`
монтирует `- /var/run/docker.sock:/var/run/docker.sock` и несёт об этом врезку в собственном
compose-файле — «🚨🚨🚨 Хостовой docker.sock … Это НЕ dind», «Деплойный раннер получает хостовой
docker.sock — риск принят». Хостовый сокет монтирует также агент наблюдаемости `vm-alloy` (для
discovery контейнеров).

**Правило, как оно практикуется на самом деле:** *сборочные* раннеры ходят через DinD и хостового
сокета не касаются; *деплойный* — сознательное исключение, потому что деплой по определению
управляет хостовым демоном. Наш раннер сборочный, поэтому DinD остаётся верным выбором и совпадает
с четырьмя из пяти соседей. Неверным было именно обоснование: абсолютное правило было выведено из
выборки, которая и посчитана неправильно, и опровергается одним из собственных членов.

Отдельно: четвёртый **org**-раннер `s2-prod-deploy` id 17 стоит на **s2**, а не на s1, и в счёт
хаба не входит вовсе — это независимый источник путаницы в исходном тексте.

### Task 2.3 — свой `dind`, не общий с раннером 1

**Решение: у раннера 2 свой сайдкар `dind2` (`192.168.226.5`), не общий с `dind` раннера 1
(`.2`).** Обоснование и цена:

- **Что даёт.** Общий `dind` сделал бы единственный сайдкар точкой отказа для **обоих** раннеров —

## D15. Секреты фронтенда живут в OpenBao по образцу `CRM/PRIONEX_HUB` — решение принято против рекомендации, и рекомендация была слабее

**Что это.** На s1 работает `forgejo-openbao` (OpenBao 2.6.1), о котором в плане миграции нет ни
слова. Обнаружен при реализации Story 1.11. На одном инстансе живут два несовместимых паттерна:

| владелец | паттерн |
|---|---|
| `CRM/PRIONEX_HUB` | Forgejo держит только bootstrap-креденшлы AppRole (`OPENBAO_ADDR`, `OPENBAO_{DEV,PREPROD,PROD}_ROLE_ID`, `…_SECRET_ID`); прикладные значения читаются из OpenBao в рантайме |
| `Telecom/aggressive_dialer`, org `Infra` | та же форма под старыми именами `VAULT_ROLE_ID` / `VAULT_SECRET_ID` |
| `CRM/api-prionex` | **OpenBao не используется вовсе** — пятнадцать боевых секретов лежат прямо в repo-секретах Forgejo (`PREPROD_JWT_SECRET`, `PREPROD_POSTGRES_PASSWORD`, `PREPROD_ENCRYPTION_KEY_VERSIONS` и другие) |

**Решение (Oleg, 13.08.2026): `fe-prionex` следует `PRIONEX_HUB`.** Не выбрать было нельзя:
молчание породило бы на инстансе третий паттерн по случайности.

### Рекомендация была другой, и это записано намеренно

Рекомендовался образец `api-prionex` — на том основании, что фронтенд потребляет ровно один
креденшл (токен реестра), который уже лежит в org-секретах, и цепочка AppRole добавляет
зависимость ни за чем. **Решение оказалось лучше рекомендации**, и причина — не в
администрировании, а в том, что чтение воркфлоу хаба показало закалку, купленную чужим
инцидентом:

- Логин AppRole собирается через `jq -n` и подаётся в `bao write auth/approle/login -` на
  **stdin** — именно затем, чтобы `role_id` и `secret_id` не попали в `argv`, где `/proc` открывает
  их всему хосту.
- Токен OpenBao маскируется `::add-mask::` и `unset`-ится сразу после чтения KV.
- Имена ключей, вернувшихся из OpenBao, валидируются перед экспортом; отвергаются
  `PATH|LD_PRELOAD|LD_LIBRARY_PATH|IFS|BASH_ENV|ENV|SHELLOPTS|BASHOPTS|HOME|TMPDIR|DOCKER_CONFIG|DOCKER_HOST|BAO_*|VAULT_*|GITHUB_*`
  — с врезкой в коде о том, что подложенное значение секрета **уже угоняло** `PATH` в `/tmp/pwned`
  в живом инциденте.
- Секреты не касаются диска: нет `mktemp`, креденшлы реестра доходят до `curl` только через `-K -`.

Унаследовать это дешевле, чем написать заново, и дороже стоит, чем сэкономленная зависимость.

### Чего решение **не** покупает

**Конфиденциальности.** Шесть значений `VITE_*` — публичные URL, вшитые в бандл, который любой
посетитель читает в devtools. Хранение их в OpenBao покупает единообразие с соседями и рабочую
цепочку на случай, когда у фронтенда появится настоящий секрет. Story 1.12 не имеет права
утверждать иное.

### Что провижнено и измерено 13.08.2026

Через `admin`-сессию Oleg — после того как `token create` отказался выпустить узкий
provisioner-токен: OpenBao позволяет токену порождать только детей с политиками, входящими в его
собственные, а `fe-prionex-provisioner` в `[admin default]` не входил. Сама политика записалась;
не удалось именно создание токена.

| объект | значение |
|---|---|
| политики | `fe-dev-read`, `fe-pre-prod-read`, `fe-prod-read` — каждая даёт `read` на `secret/data/fe/<env>/*` и `read,list` на `secret/metadata/fe/<env>/*`, и ничего больше |
| роли | `fe-dev`, `fe-pre-prod` — `secret_id_ttl 0`, токен `10m/15m` (зеркалит `hub-dev`) |
| | `fe-prod` — `secret_id_ttl` **7200h** (число Oleg; у прод-роли хаба `720h`), токен `15m/15m` |
| KV (v2) | `secret/fe/dev/app`, `secret/fe/pre-prod/app`, `secret/fe/prod/app` |

**Движок KV — v2**, установлено от политики `hub-dev-read` (даёт `secret/data/…` и
`secret/metadata/…`); `sys/mounts/secret` политике `admin` запрещён, прочитать напрямую нельзя.

**Изоляция измерена, а не заявлена: девять проверок, девять прохождений.** Каждая роль логинилась
по AppRole и пробовала все три пути — свой читает, на двух чужих отказ. Тестовые `secret_id`
выпускались с `num_uses=1` и умирали на первом использовании, поэтому **от той сессии не осталось
ни одного живого значения** — шесть `role_id`/`secret_id` для Story 1.12 добываются заново.

**Значения не выдуманы.** Прод — `VITE_API_BASE_URL=https://api.crm-prionex.online` и
`VITE_WS_URL=wss://api.crm-prionex.online` — прочитаны **из бандла, который прод реально отдаёт**
(`/assets/index-BfP68FMT.js`); это сильнее любого конфига, потому что при варианте C контейнер не
несёт `VITE_*` в окружении вовсе — они вшиты на сборке. Совпадают с фоллбэками `CD.yml:47-51`,
значит секреты GitHub либо держат то же самое, либо не заданы. DEV — оттуда же. **PRE-PROD —
литеральный плейсхолдер** `PLACEHOLDER-preprod-backend-not-provisioned`: бэкенда нет (отложено
Story 1.6), и он назван так, чтобы его нельзя было принять за значение.

### Имена не выводятся друг из друга

Секреты Forgejo несут `PREPROD`, потому что так у хаба; роль называется `fe-pre-prod`, путь —
`secret/fe/pre-prod/app`. **Ни одно из трёх не получается из другого склейкой строк.** Путь,
собранный из имени секрета, даёт `secret/fe/preprod/app`, которого не существует.

### Сетевое препятствие, найденное здесь, а не в середине Эпика 5

**Ни один раннер не делил сеть с OpenBao,** и очевидный способ не работает: джоб-контейнеры
создаются во **вложенном dind** (`docker_host: tcp://dind:2375`), у которого список сетей —
только `bridge`, `host`, `none`. Хостовой `forgejo_forgejo` там не существует, поэтому
`container.network: "forgejo_forgejo"` в конфиге раннера его не разрешит. Порт 8200 опубликован
только на `10.70.0.1` и `127.0.0.1`, и контейнер на хостовом bridge не достаёт ни до одного
(измерено: `000`).

**Решено подключением обоих dind-движков к `forgejo_forgejo`** и обращением к OpenBao по IP:

```
forgejo-runner-fe-prionex-dind     runner=192.168.226.2   forgejo_forgejo=172.20.0.6
forgejo-runner-fe-prionex-dind-2   runner=192.168.226.5   forgejo_forgejo=172.20.0.7
forgejo-openbao                    forgejo_forgejo=172.20.0.5
```

Измерено из контейнера внутри **каждого** dind с `--add-host openbao:172.20.0.5`:
`http://openbao:8200/v1/sys/seal-status` → **200** на обоих.

🔴 **Сначала был подключён только первый dind.** Второй нашёлся изолированным и подключён после.
Останься это незамеченным — джобы, попавшие на раннер 2, падали бы, пока раннер 1 работает: это
перемежающийся отказ без внятной причины, в паре раннеров, которую Story 1.9 строила именно ради
распределения нагрузки. **Любое изменение одного раннера должно применяться и проверяться на
обоих**; сверка дрейфа в `docs/runners/README.md` сейчас раннеры между собой не сравнивает.

⚠️ **Строка `--add-host openbao:172.20.0.5` хрупка ровно так же, как уже существующая
`--add-host git.crm-prionex.com:10.67.0.1`:** это IP контейнера, вбитый руками. Пересоздадут
OpenBao — адрес может смениться, и каждый деплой упадёт на невнятной ошибке соединения. Story 1.12
обязана добавить preflight, который падает громко и называет причину, вместо того чтобы за него
говорил таймаут `bao`.

### Что это отменяет в [D6](#d6)

### Открытые вопросы, у которых нет владельца

1. **`secret_id` для `fe-prod` живёт 7200h (~10 месяцев), и ничто его не ротирует.** Требование не
   исчезает, а переезжает за пределы первого года. Дату выпуска обязана записать Story 1.12 —
   иначе истечение придёт как одновременный отказ всех прод-деплоев без видимой причины.
2. **У самого хаба прод-`secret_id` истекает каждые 720h**, и ничего видимого его не обновляет. Не
   наша система; сказать той команде стоит до того, как их прод-деплой упрётся в протухший
   креденшл.
3. **Мониторинга истечения креденшлов в плане нет вообще.** Минимум — документация Эпика 7;
   вероятнее, нужен владелец до того, как от этого будет зависеть PROD.
4. **Наличие `bao` в джоб-образе не проверено.** Шаг чтения из AC4 Story 1.12 требует CLI на

### Дополнение 13.08.2026 — цепочка заведена в Forgejo и доказана

Семь repo-секретов созданы на `CRM/fe-prionex` (`OPENBAO_ADDR` = `http://openbao:8200` — имя, а не
IP, чтобы смена адреса стоила одной правки конфига, а не семи перезаписей). На org-уровне AppRole
не заведён ни один. До этой записи у репозитория **не было ни одного секрета и ни одной
переменной**, поэтому любое восьмое имя там — находка.

**Каждый `secret_id` доказанно логинится до того, как попал в Forgejo** — три логина, три `200`.
Это не педантизм: значения секретов Forgejo не читаются обратно, а неверный `secret_id` падает так
же, как отсутствующий, но диагностируется втрое дольше. `OPENBAO_PROD_SECRET_ID` выпущен
2026-08-13T11:02:06Z и **истекает 2027-06-09 10:56 UTC**; не ротирует его ничто.

Попутно вычищено семь бесхозных `secret_id`, наминченных неудачной попыткой (3 у `fe-dev`, по 2 у
остальных). Урок, который проект уже знает про токены Forgejo, действует и для OpenBao: минт
дешёвый, убирать за собой некому.

🔴 **Метод проверки изменён, и это важнее результата.** Первый прогон матрицы изоляции показал, что
каждая роль читает все три пути — противоположность записи от 13.08. Причина оказалась в
`/usr/local/bin/bao` на s1: это **не клиент, а `sh`-обёртка 755**, оставленная Story 3.2 хаба с
собственной пометкой «удалить после провижининга», которая делает `docker exec … -e BAO_TOKEN …`.
При пустом `BAO_TOKEN` docker не передаёт ничего, и клиент внутри контейнера берёт токен с
политикой `admin`. Девять «успехов» были им. Голый HTTP ведёт себя верно: без заголовка — `403`, с
пустым — `403`, с admin — `200`. **Все утверждения про OpenBao в Эпиках 3–6 делаются по HTTP с явным
`X-Vault-Token`, а не через хостовую обёртку.** Повторный прогон дал чистую диагональ, девять из
девяти, при трёх работающих контролях.

### Механизм чтения — решение Oleg 13.08.2026: ставим CLI, шаг наследуем

**Принято: `apk add --no-cache openbao=2.6.0-r0 jq`, дальше шаг хаба почти дословно.**

Отвергнуто **(b) — только HTTP, без CLI**: экономит ~1 секунду и не устраняет главного. `jq` для
структурного извлечения нужен всё равно (разбирать JSON через `sed` — ровно тот приём, на котором у
хаба значение секрета угнало `PATH` в `/tmp/pwned`), значит обращение к зеркалу остаётся, просто
становится меньше. За эту секунду пришлось бы самим отвечать за пять свойств защиты вместо того,
чтобы унаследовать версию, которая **уже пережила** реальный угон `PATH` и два провала маскирования,
найденных прогоном, а не чтением.

Отвергнуто **(c) — свой образ**: метка `docker-build` привязана к образу на регистрации
(Story 1.7/1.9, Trap 5), смена означает перерегистрацию либо `container:`-оверрайд в одной джобе из
всех.

**Цифры, на которых стоит решение** (три прогона из джоб-эквивалентного контейнера, 13.08):
старт контейнера 0.54/0.55/0.55 с; он же с `apk add --no-cache openbao jq` — 1.94/1.92/1.85 с.
**Инструменты стоят ~1.35 с.** Первоначальная рекомендация была (b) и опиралась на допущение, что
`bao` пришлось бы качать бинарём с GitHub вручную; Alpine 3.24 пакетирует и `openbao-2.6.0-r0`, и
`jq-1.8.1-r0`, что меняет арифметику.

**Какой образ участвует, теперь сказано явно:** значения нужны на **сборке** (вариант C вшивает их в
бандл, Story 3.3 передаёт `--build-arg`), то есть джоба идёт на метке `docker-build` → Alpine.
`node-20` (Debian) пакета OpenBao не имеет, но там это и не выполняется. Чтение на деплое в
Эпиках 4–6 приземляется на деплой-раннеры целевых хостов, где `bao` у хаба стоит хостовым пакетом —
это решают те истории.

⚠️ **Два обязательства, которые несёт это решение.** Версия **пинуется** (`openbao=2.6.0-r0`), иначе
апгрейд Alpine прилетит сюрпризом на боевом деплое; клиент на один патч младше сервера 2.6.1,
совместимость ожидаема и **не проверена**. И зеркало Alpine оказывается на критическом пути каждой
сборки — preflight обязан различать «нет `bao`» и «OpenBao недоступен», это разные причины с разными
починками, а свалить их в один таймаут значит повторить ошибку, которую хаб оплатил окном
break-glass на s2.

**Требования:** `epics.md` Story 1.12 (переписана `sprint-change-proposal-2026-08-13-openbao.md`
§4.1), Story 3.3 (§4.3 — источник значений `VITE_*`). Потребители — Stories 3.3, 4.3, 5.2, 6.4:
каждый воркфлоу деплоя получает шаг чтения из OpenBao в форме, зафиксированной здесь, а не
изобретает свою.

## Восстановление правила очистки реестра (Story 1.11)

Правило живёт **только в базе Forgejo**. API и CLI для правил очистки не существует, из репозитория
оно не восстанавливается, поэтому значения полей записаны здесь дословно и предназначены для
копирования. Путь: `CRM` → Settings → Packages → правило.

```
enabled          = true
type             = container
match full name  = true          ← обязательно; без него правило видит только имя версии,
                                   а оно одинаково у всех 86 контейнерных пакетов организации
keep count       = 0             ← намеренно ноль: keep_count сортирует по свежести вперемешку
                                   со строками-дайджестами, и день сборок веток вытеснил бы
                                   теги деплоя из-под защиты
remove days      = 14
```

`Remove versions matching` — одна строка:

```
fe-prionex/.+
```

`Keep versions matching` — одна строка:

```
fe-prionex/(prod-current|preprod-current|latest|buildcache|v?\d+\.\d+\.\d+.*|(pre)?prod-[0-9a-f]{7,64}|sha-[0-9a-f]{7,64}-(pre)?prod|sha256:[0-9a-f]{64})
```

⚠️ **Клауза `sha256:[0-9a-f]{64}` должна стоять внутри скобок**, последней альтернативой перед `)`.
При первой правке её дописали снаружи группы — паттерн якорится целиком, поэтому такая ветка
требует, чтобы всё полное имя было `sha256:<64 hex>`, а при `match full name` имя всегда начинается
с `пакет/`. Клауза оказалась мёртвой. Поймано сравнением сохранённой строки с эталоном; глазами не
видно.

⚠️ Клауза `sha256:` инертна на Forgejo 15.0.5 — правила, судя по всему, не удаляют строки-дайджесты
(вывод недо-доказан, см. changelog 13.08). Оставлена как страховка на случай смены поведения.
