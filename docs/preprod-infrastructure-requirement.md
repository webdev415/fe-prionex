## 1. Зачем это нужно и что сломается без этого

Мы поднимаем среду PRE-PROD — стенд, на котором релиз-кандидат проверяется **перед** выкаткой в
продакшн. Смысл такого стенда ровно один: то, что на нём проверено, должно быть тем же самым, что
поедет в прод.

**Если PRE-PROD подключить к существующей общей сети `crm-network`, этот смысл теряется — молча.**

Механика такая. Фронтенд ходит в бэкенд не по IP и не по конфигурируемому адресу, а по **имени
сервиса** `crm-kong-gateway`, зашитому в конфиг nginx:

```
nginx.conf:39   set $kong_upstream http://crm-kong-gateway:8000;   # location /api/
nginx.conf:50   set $kong_upstream http://crm-kong-gateway:8000;   # location /ws/
```

Этот конфиг **запекается в образ** на сборке (`Dockerfile.prod:34`), и образ побайтово одинаков для
всех стендов. То есть указать другому стенду другой адрес шлюза **негде** — ни переменной
окружения, ни файлом на сервере.

Внутри общей сети `crm-network` имя `crm-kong-gateway` резолвится в **уже существующий, DEV-овский**
Kong. Контейнер PRE-PROD поднимется, отдаст страницу, и все запросы уйдут в DEV.

**Как это выглядит со стороны:** стенд работает. Ошибок нет. Тесты проходят. И каждый релиз,
проверенный на этом стенде, на самом деле проверен против **данных DEV и версий сервисов DEV** — а
в продакшн он поедет на основании этой проверки. Отказ здесь не громкий, а тихий, и обнаружится он
в проде.

Именно поэтому мы просим не «ещё один контейнер», а **изолированный сетевой контур**.

## 2. Что мы просим

### 2.1. Отдельная Docker-сеть `crm-network-preprod` на `s1`

Создаётся и **сопровождается инфраструктурной командой**, а не поднимается на лету скриптом
деплоя. Сегодня общая сеть создаётся именно так — `docker network create crm-network 2>/dev/null ||
true` (`.github/workflows/CD.yml:185`), — и для среды, на которой валидируется релиз, это
неприемлемо: у сети должен быть владелец.

### 2.2. Второй экземпляр Kong в этой сети

Маршрутизирующий на **PRE-PROD-экземпляры** бэкенд-сервисов. Как минимум те, что уже используются
фронтендом:

| маршрут | сервис | порт |
|---|---|---|
| `/api/v1/auth/*` | Auth Service | 8001 |
| `/api/v1/clients/*` | Client Service | 8002 |
| `/api/v1/calls/*` | Call Service | 8005 |
| `/ws/calls` | Call Service WebSocket | 8005 |

Список взят из `.env.example:17-20` и заканчивается там строкой `... etc` — то есть он **не
исчерпывающий**. Полный состав маршрутов на стороне бэкенда, просим подтвердить вас.

### 2.3. 🚨 Критическое ограничение по имени, которое иначе всплывёт поздно

**Внутри `crm-network-preprod` этот Kong должен быть доступен под именем `crm-kong-gateway` на порту
`8000`** — либо как имя контейнера, либо как сетевой алиас.

Это не пожелание по стилю. Как показано в §1, имя запечено в образ, и обойти его нечем. Если шлюз
получит другое имя — например `crm-kong-gateway-preprod`, — фронтенд PRE-PROD не заработает вообще,
и починить это можно будет только пересборкой образа, то есть нарушив главный принцип: **в прод
едет тот же самый образ, что проверялся**.

Разные сети изолируют пространства имён, поэтому одинаковое имя в двух сетях конфликта не создаёт.

### 2.4. 🚨 Вопрос, который сетевой изоляцией не закрывается

**Стоят ли за этим Kong собственные экземпляры сервисов с собственными базами данных, или они
смотрят в БД DEV?**

Спрашиваем прямо, потому что второй Kong перед сервисами, работающими с данными DEV, воспроизводит
ровно ту же фиктивную валидацию, ради предотвращения которой написан весь этот документ — только с
правильной на вид схемой сети.

Соответственно: **кто и по какому триггеру обновляет версии этих сервисов относительно
релиз-кандидата?** Если PRE-PROD-бэкенд отстаёт или опережает прод, стенд снова проверяет не то.

### 2.5. Доступность снаружи: DNS, TLS и порт

| что | значение |
|---|---|
| DNS-имя стенда | `preprod.crm-prionex.online` |
| TLS-сертификат | на это имя |
| Публикуемый порт на `s1` | **8081** |
| Внешнее имя PRE-PROD Kong | `api.preprod.crm-prionex.online` (+ сертификат) |

Именование продолжает уже существующий шаблон: `api.crm-prionex.online` для прода и
`api.dev.crm-prionex.online` для DEV (`.github/workflows/CD.yml:47,51,57,61`).

**Порт 8081 — постоянная аллокация, а не временная.** На `s1` будет три фронтенд-стенда
одновременно: legacy `8080` (срока вывода нет), новый DEV `8082`, PRE-PROD `8081`.

**Уточняющий вопрос по TLS.** Контейнер фронтенда слушает голый HTTP (`Dockerfile.prod:37`
`EXPOSE 80`, в `nginx.conf` нет ни одной директивы `ssl`), то есть TLS терминирует что-то перед ним.
Просим подтвердить, что именно, и на чьей стороне лежит сертификат — в нашем плане это место не
описано.

### 2.6. CORS и cookies

Фронтенд ходит в API с `withCredentials: true` (`src/lib/api.ts:18`), то есть шлёт cookie
кросс-доменно. PRE-PROD Kong должен отдавать `Access-Control-Allow-Origin` **точным значением**
`https://preprod.crm-prionex.online` (не `*`, с `*` браузер запрос с credentials отклонит) и
`Access-Control-Allow-Credentials: true`.

## 3. Что нам нужно в ответ

**Дата.** Не «в планах», а срок, на который мы можем ставить Эпик 5.

Отказ или сокращение объёма — например «используйте общую `crm-network`, добавим маршрут в
существующий Kong» — **это тоже полноценный ответ**, и он полезнее молчания: он позволит нам
перепланировать заранее, а не обнаружить несовпадение в момент запуска стенда. Просим в этом случае
явно указать, какой из пунктов §2 не выполняется, — каждый из них ломает свою часть плана.
