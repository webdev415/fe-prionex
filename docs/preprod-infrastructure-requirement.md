## 1. Зачем это нужно и что сломается без этого

Мы поднимаем среду PRE-PROD — стенд, на котором релиз-кандидат проверяется **перед** выкаткой в
продакшн. Смысл такого стенда ровно один: то, что на нём проверено, должно быть тем же самым, что
поедет в прод.

**Если PRE-PROD подключить к существующей общей сети `crm-network`, этот смысл теряется — молча.**

Механика такая. Фронтенд ходит в бэкенд не по IP и не по конфигурируемому адресу, а по **имени
сервиса** `crm-kong-gateway`, зашитому в конфиг nginx:

```
nginx.conf:39   set $kong_upstream http://crm-kong-gateway:8000;   # location /api/
nginx.conf:50   set $kong_upstream http://crm-kong-gateway:8000;   # location /ws/
```

Этот конфиг **запекается в образ** на сборке (`Dockerfile.prod:34`), и образ побайтово одинаков для
всех стендов. То есть указать другому стенду другой адрес шлюза **негде** — ни переменной
окружения, ни файлом на сервере.

Внутри общей сети `crm-network` имя `crm-kong-gateway` резолвится в **уже существующий, DEV-овский**
Kong. Контейнер PRE-PROD поднимется, отдаст страницу, и все запросы уйдут в DEV.

**Как это выглядит со стороны:** стенд работает. Ошибок нет. Тесты проходят. И каждый релиз,
проверенный на этом стенде, на самом деле проверен против **данных DEV и версий сервисов DEV** — а
в продакшн он поедет на основании этой проверки. Отказ здесь не громкий, а тихий, и обнаружится он
в проде.

Именно поэтому мы просим не «ещё один контейнер», а **изолированный сетевой контур**.

## 2. Что мы просим

### 2.1. Имена сетей принимаем ваши

Ваш стек параметризован через `STACK`, сети называются `crm-dev-network`, `crm-preprod-network`,
`crm-prod-network`. Наш план называл PRE-PROD-сеть `crm-network-preprod` — **мы отказываемся от
своего имени в пользу вашего.** Ваша схема консистентна на трёх средах и записана в трёх планах;
наше имя было единичным. У нас имя сети берётся из переменной, цена перехода — одна строка в `.env`
на стенд.

### 2.2. 🚨 Единственное, что мы просим сделать — сетевой алиас

**Внутри сети каждого стенда Kong должен отвечать на имя `crm-kong-gateway` на порту `8000`.**

У вас `container_name: ${STACK:-crm}-kong-gateway` (`docker-compose.server.yml:684`), то есть на
новых стендах получится `crm-dev-kong-gateway`, `crm-preprod-kong-gateway`, `crm-prod-kong-gateway`.
Наш фронтенд обращается к шлюзу по литеральному имени `crm-kong-gateway` (`nginx.conf:39,50`), и это
имя **запечено в образ** (`Dockerfile.prod:34`). Образ побайтово одинаков для всех сред — на этом
стоит промоушен: в прод едет ровно тот образ, что проверялся на PRE-PROD. **Указать другое имя для
конкретного стенда нам негде.**

Просьба: добавить Kong **сетевой алиас** `crm-kong-gateway` в сети стенда. Одна строка на стек, ваш
`container_name` остаётся как есть, разные сети изолируют пространства имён — конфликта одинаковых
алиасов в трёх сетях не возникает.

```yaml
  kong:
    container_name: ${STACK:-crm}-kong-gateway
    networks:
      <сеть стенда>:
        aliases:
          - crm-kong-gateway        # ← фронтенд ищет это имя, оно вшито в его образ
```

**Порт менять не нужно и не просим.** Проверили: `KONG_PROXY_LISTEN: "0.0.0.0:8000, ..."`, маппинг
`"${KONG_PORT:-8000}:8000"` — `KONG_PORT=8330` в вашем PROD-плане меняет только публикуемый порт
хоста, внутри сети Kong везде на 8000. Наш хардкод порта верен.

**Если алиас не поставить, отказ будет тихим по нашей вине, а не по вашей:** контейнер фронтенда
поднимется, отдаст страницу, а `/api/` и `/ws/` не разрезолвятся. Наша Story 5.1 обязана проверять
резолвинг **изнутри работающего контейнера** именно поэтому.

### 2.4. Доступность снаружи: DNS, TLS и порт

| что | значение |
|---|---|
| DNS-имя стенда | `preprod.crm-prionex.online` |
| TLS-сертификат | на это имя |
| Публикуемый порт фронтенда на `s1` | **8081** |
| Внешнее имя PRE-PROD Kong | `api.preprod.crm-prionex.online` (+ сертификат) |

Именование продолжает существующий шаблон: `api.crm-prionex.online` для прода и
`api.dev.crm-prionex.online` для DEV (`.github/workflows/CD.yml:47,51,57,61`).

**Порт 8081 — постоянная аллокация.** На `s1` будет три фронтенд-стенда: legacy `8080` (срока вывода
нет), новый DEV `8082`, PRE-PROD `8081`.

**Уточняющий вопрос по TLS.** Контейнер фронтенда слушает голый HTTP (`Dockerfile.prod:37`
`EXPOSE 80`, в `nginx.conf` нет ни одной директивы `ssl`) — TLS терминирует что-то перед ним. Просим
подтвердить, что именно, и на чьей стороне сертификат.

### 2.5. CORS и cookies

Фронтенд ходит в API с `withCredentials: true` (`src/lib/api.ts:18`), то есть шлёт cookie
кросс-доменно. PRE-PROD Kong должен отдавать `Access-Control-Allow-Origin` **точным значением**
`https://preprod.crm-prionex.online` (не `*` — с ним браузер отклонит запрос с credentials) и
`Access-Control-Allow-Credentials: true`.

## 3. Что нам нужно в ответ

**Дата.** Не «в планах», а срок, на который мы можем ставить Эпик 5.

Отказ или сокращение объёма — например «используйте общую `crm-network`, добавим маршрут в
существующий Kong» — **это тоже полноценный ответ**, и он полезнее молчания: он позволит нам
перепланировать заранее, а не обнаружить несовпадение в момент запуска стенда. Просим в этом случае
явно указать, какой из пунктов §2 не выполняется, — каждый из них ломает свою часть плана.
